Purpose

Make component identity a first-class shared capability in Propellr. The initial product is component-aware deduplication: turn repeated occurrences into actionable repair scopes without losing evidence. The same model then supports state exploration, agent targeting and verification of shared fixes.

Revised priority: component attribution becomes the first Jev evaluation, ahead of the general probe-selector experiment in the initial recommendations. Component intelligence itself must work without Jev. The provider earns its place by improving ambiguous attribution over useful deterministic baselines.

Preserve the agreed accessibility baseline and independent canonical reference. This plan adds identity and investigation capabilities, not axe-core APIs, new rule coverage or a probabilistic replacement for exact browser checks. Planning is authorized; implementation, dependencies, model spend, PR delivery and production use are not.

Problem

Current reporting groups by exact rule version and scoped target within one document generation. That preserves correctness, but cannot tell an agent whether 80 unlabeled buttons need 80 edits or two. Selector equality, visual similarity and common ancestry cannot answer that question reliably.

Observed cases Required interpretation What must not happen
70 favorite buttons in ProductCard; 10 in RecommendationTile. Similar markup. Two candidate repair scopes if each template omits its label. Merge unrelated implementations because their DOM looks alike.
Desktop/mobile ProductCard variants have different markup but the same faulty binding. One supported repair scope with separate variant obligations. Split solely on markup, or assume one tested variant proves all others.
Same IconButton primitive receives an empty label from one caller. Renderer is IconButton; responsibility may lie in caller binding or data. Blame the primitive or group every IconButton finding together.
Identical sibling cards; one has missing product data. Same definition, different instance-level cause. Treat component membership as proof of a common defect.

These are target behaviors for new original fixtures, not observed results. Current nine bounded implementations, 96 unimplemented catalog rules, fixture-restricted host and full-scan fallback remain the baseline. Naming evidence currently excludes name text; semantic capture needs a new explicit policy.

Architecture

Introduce a bounded component evidence model shared by browser collection, host inference, portable grouping and agent consumers. Begin with ordinary TypeScript records and indexed relations, not a graph database or a platform. Keep authoritative scan output and identity enrichment on separate paths.

Identity and evidence contract

Entity Required meaning Identity boundary
Definition Application namespace, definition ID, build/revision, optional source ref and registered part schema. Display name, CSS class or role is not a definition ID. No automatic cross-build continuity.
Instance Definition reference if known, session/page/document, epoch-bound element membership and declared variant/state. Repeated instances remain distinct. Rerender, list-key reuse, virtualized rows and navigation invalidate stale mappings.
Part Meaningful element role within the component: favorite-control, label, trigger or error-region. Part keys are component-local, possibly one-to-many; arbitrary DOM order is not stable identity.
Relations Rendered-by, composed-in, slotted-from and label/content-supplied-by, when supported by evidence. DOM parentage differs from framework ownership. Portals, fragments, slots and external labels need explicit relations or unknowns.
Attribution assertion Target and candidate IDs, evidence references, collector/model/rubric versions, source kind, status and conflict reasons. Separate source provenance from confidence. Declared, source-linked, inferred, reviewed and experimentally supported are not interchangeable.
Repair scope Proposed owner/callsite or data binding, part, compatible rule/check defect signature, affected variants and occurrence references. A shared definition is necessary evidence in some cases, never sufficient proof of a shared fix.

Inputs derive from strict schemas at the host/portable boundary. Browser analysis imports types only. Use discriminated states for supported, inferred, unknown, conflicting, stale and unavailable results; absence of a candidate is not a negative accessibility verdict. A state digest is correlation metadata, not anonymization.

Two evidence paths, one contract

  1. Instrumented: host loads an approved build manifest; a minimal opt-in bridge maps live elements to definition, instance and part IDs. Correlate registration with current document/build. Source locations and callsites stay local unless separately approved for export. Page markers alone are untrusted declarations, not verified source ownership.
  2. Uninstrumented: collect bounded structural/role/relationship fingerprints and approved local text. Generate candidate component boundaries/templates in code. Unknown templates receive opaque, build-scoped IDs, not invented framework names. Jev may classify membership, parts and variants among those candidates; source identity remains unknown without source evidence.

Start with a framework-neutral manifest fixture. Add one real opt-in Vue integration only after the evidence contract works. Do not scrape private Vue/React internals, assume production DevTools hooks exist, or use nearest DOM ancestor as universal ownership. A host-approved manifest does not attest a hostile page's live execution: source-linked attribution is scoped to the cooperative instrumented application and recorded build provenance, not a security guarantee. Page code can impersonate valid registrations; do not promote these into authorization evidence. Denied frames and closed roots stay unobserved.

Grouping is a repair hypothesis, not destructive merging

A candidate key combines application/build scope, supported owner or callsite, part, rule/check version and defect mechanism. Variant conditions refine it. Shared rule ID or name is not enough. Findings spanning multiple targets/components need relationship evidence or remain ungrouped.

  • Keep the current IssueGroup and applyGate semantics intact. Add a separate versioned component/repair view referencing raw scan and occurrence IDs. Never put probabilistic groups inside the current authoritative group array.
  • Expose counts separately: violation occurrences, existing exact-target issues, supported repair scopes, suggested repair scopes and unattributed occurrences. “Two candidate fixes, 80 occurrences” is allowed; “two confirmed defects” requires cause evidence.
  • Related hypotheses can overlap. Do not sum overlapping groups as unique defects or hide ambiguous members. Each displayed member retains its attribution basis.
  • No transitive union from model similarity: A≈B and B≈C cannot establish A=C. Require common-owner/cause evidence and conflict checks across every admitted member.
  • A template/source mapping establishes membership, not defect cause. Support a shared repair with reviewed binding evidence or a controlled intervention that changes the predicted instances and not controls.
  • Version every matcher and grouping decision. Preserve historical membership and explicit split/supersession; do not rewrite past reports after model changes.

Closing a repair scope requires current evidence for every claimed affected member or explicit removed/inapplicable disposition under reviewed identity and coverage rules. Untested variants, narrower scans, missing targets and partial coverage cannot close a group. Cross-build repair receipts stay separate from existing within-document issue lifecycle.

Jev's bounded job

Ask direct questions over code-generated candidates: which component contains this element, which registered part it serves, whether two variants fit a supplied definition, and whether observed evidence supports a particular cause hypothesis. Separate those judgments. Batch questions sharing relevant state; do not send the entire DOM or assume answers within a request depend on one another.

Reserve explicit none/insufficient-evidence choices; stay within the 255-option limit including sentinels. Larger catalogs require a deterministic shortlist or measured hierarchical retrieval. Report candidate recall separately from decision accuracy: Jev cannot choose a missing answer. Measure unknown-component discovery, not only matching a conveniently supplied correct candidate.

Jev is text-only, not a source inspector or a visual oracle. Its confidence is not a probability that one patch fixes every instance. Page content can steer its decisions. Host checks evidence provenance, allowed IDs, output schema, deadlines and freshness; models never grant permission or waive findings.

Decisions, dependencies and exclusions

Relationship to existing work

Phases 1–2 can run against explicit scans without waiting for continuous observation or the remaining rule catalog. Phase 3 needs bounded host delivery; it must coordinate with any concurrent realtime contract changes rather than duplicate schedulers. Phase 4's real-agent lane depends on approved same-page conformance, but scripted source-intervention tests do not.

This plan promotes component inference from a later reporting suggestion into shared architecture. General contextual review and prose claim checking remain useful follow-ups; they are not extra requirements hidden inside this component slice.

Approval gates

  • Freeze protocol bounds, metrics, corpus split and thresholds before implementation/evaluation. Proposed numeric gates here are not measured results or spending authorization.
  • Approve provider credentials, exact models, client dependencies, exported synthetic fields, region/retention and numeric budget before live inference. No external image generation needed.
  • Review TypeSafe's applicable MCA for output reuse, model distillation and adversarial testing. No assumption that Jev labels can train a replacement model. The architecture stays provider-neutral and useful offline.
  • Approve Vue/test dependencies and opt-in source registration separately. No silent broadening to customer repositories, live apps, global tools or daily-driver browsers.

Key risks and responses

  • Missing candidates: benchmark candidate recall and boundary discovery. No model can recover an omitted component through a closed-set answer.
  • Wrong shared cause: separate definition/part recognition from repair responsibility; test caller and instance-data counterexamples and controlled source interventions.
  • Unknown frameworks: structural membership can be useful while framework/source ownership stays unknown. Never manufacture source files from rendered markup.
  • False confidence: evaluate grouped holdouts, uncertainty and selective prediction. Stable model answers and type-safe outputs do not prove identity.
  • Privacy and prompt injection: minimize capture, retain source/props locally by default, redact before egress and preserve deterministic grants. Redaction that removes essential evidence must cause abstention.
  • Asynchronous staleness: current scan epochs are not perpetual freshness. Recollect or verify current bindings before acting; continuous observation requires its separate implemented contract.
  • Cost/latency: published Jev limits are currently 1,200 requests/minute and 250,000 tokens/second, subject to change. Batch by relevant evidence, not per DOM node. No network calls on the exact scan critical path.

Deliberate exclusions

No graph database, package split, generic plugin platform, additional rule batch, visual component recognition, closed-root access, automatic cross-origin injection, React adapter, universal production-framework introspection, learned rule skipping, inferred gate exceptions, source patch generation, autonomous merging or production deployment.

Research grounding

Jev brief records reviewed API limits, failure modes, SDK defaults, legal constraints and primary sources. Relevant patterns: entity alignment, closed-set candidate selection and documented failure modes. Their examples do not establish component-attribution accuracy. Novelty here is a product hypothesis about evidence-backed repair scope, not a prior-art or competitor claim.
